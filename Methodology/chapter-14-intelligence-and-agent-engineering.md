# Chapter 14: Intelligence and Agent Engineering

# Intelligence and Agent Engineering

> **CHAPTER PURPOSE** Engineer the complete intelligence system from specification and model strategy through context, harness, tools, memory, evaluation and AgentOps — as a single accountable engineering discipline, not a chain of independent experiments.

*Figure 4. OASIS engineers and evaluates the complete intelligence system.*

## Background and context

For most of the short history of applied large language models, "prompt engineering" was treated as the whole discipline: get the wording right, add a few examples, and the system would behave. That framing made sense when a system was a single call to a single model and the hard part really was the instruction. It stopped making sense once systems started retrieving evidence, calling tools, running multi-step loops, remembering things across sessions, and taking actions with real consequences. A well-worded prompt sitting on top of poor retrieval, an unbounded agent loop, or an unmonitored tool with no rollback path is not a well-engineered system — it is a good sentence in a fragile machine. This chapter treats the whole machine as the unit of engineering. The system equation below is the organizing idea for the rest of Part III: an AI system is the sum of nine engineered layers, and each layer has its own failure modes, its own design discipline, and its own place in this chapter.

> **SYSTEM EQUATION** AI system = Model + Context + Harness + Tools + Workflow + Memory/State + Controls + Evaluation + Runtime.

That shift — from prompt engineering to system engineering — is also a shift in where confidence has to come from. [Chapter 13](chapter-13-decision-gates-and-evidence-model.md) established that progression through the lifecycle is gated on evidence, not on calendar time or stakeholder comfort; this chapter is where that evidence gets manufactured. Solution Viability evidence, Production Readiness evidence, and Operational Acceptance evidence are all, ultimately, claims about the twelve layers engineered in this chapter — a model benchmark, a context architecture, a tool contract, a guardrail configuration, an evaluation suite. A team that cannot answer "how was this specified, selected, evaluated and controlled" for each layer has no real evidence to bring to a gate, no matter how confident it feels about the demo.

The chapter that follows this one continues the same thread from a different angle. [Chapter 15 — Data and Knowledge Engineering](chapter-15-data-and-knowledge-engineering.md) goes deep on the specific discipline introduced here in Section 3 — the governed services that supply evidence to the system — because knowledge quality turns out to be the single most common root cause of production failure in fielded systems, and it deserves a chapter of its own rather than a subsection.

Every section below states the engineering discipline and the reasoning behind it, at methodology altitude: what decisions must be made, and why they matter. It intentionally does not supply templates, YAML schemas, or worked examples — that implementation depth lives in the **engineering/** folder, written specifically as this chapter's companion. Six articles there — [Model Engineering](../engineering/model-engineering.md), [Context and Retrieval Engineering](../engineering/context-and-retrieval-engineering.md), [Tool and Integration Interface Specification](../engineering/tool-and-integration-interface-specification.md), [Harness and Orchestration Engineering](../engineering/harness-and-orchestration-engineering.md), [Memory and State Engineering](../engineering/memory-and-state-engineering.md), and [Evaluation and Reliability Engineering](../engineering/evaluation-and-reliability-engineering.md) — turn each section of this chapter into a fillable specification a build team can actually run through. The [OASIS Reference Architecture](../architecture/oasis-reference-architecture.md) does the equivalent work for the system as a whole, rendering the equation above as a component diagram. Read this chapter for the reasoning; read the engineering folder for the mechanics.

## 1. Intelligence-system specification

Every intelligence system needs a behavioral contract before it needs a model, a prompt, or a line of harness code — and that contract is what this section calls the intelligence-system specification. It states what the system must understand, decide, generate or execute; the inputs and evidence it is permitted to use; the exact shape of its expected output; the actions it may take and the ones it may not; how it behaves under uncertainty, including when it must abstain rather than guess; what "done" looks like for a given task; behavior that is explicitly prohibited regardless of how a user or an upstream system phrases a request; and the specific cases that require a human's authority rather than the system's own judgment.

The reason this has to be written down as a specification, rather than left implicit in a system prompt, is that a system prompt is instructions to the model — one component of the eventual system — while a specification is a contract the whole system is built and evaluated against, spanning the harness, the tools, the guardrails and the evaluation suite as much as the model. Teams that skip this step tend to discover the specification anyway, one production incident at a time, as each unanticipated case forces an ad hoc decision about what the system should have done. Writing the specification first means those decisions get made deliberately, with the right stakeholders in the room, instead of being made implicitly by whichever engineer happened to be on call. The [Intelligence-System Blueprint](chapter-32-templates-checklists-and-tools.md#11-intelligence-system-blueprint) is the artifact that carries this specification forward through design, build and evaluation, and the [OASIS Reference Architecture](../architecture/oasis-reference-architecture.md#1-system-equation-as-a-diagram) shows where each of its elements lands on the system diagram.

## 2. Model engineering

Model engineering is the discipline of selecting and benchmarking models against representative tasks — not against general leaderboards, which measure something else, and not by reputation, which measures something older still. The decision surface is wider than raw capability: reasoning depth needed for the task, modality (text, vision, audio, structured data), the region a model can legally and practically be deployed in, what happens to the organization's data once it reaches the model, latency tolerance, cost per successful outcome, context window, how reliably the model makes structured tool calls, and the operational realities of working with a given provider — SLA, versioning discipline, deprecation notice. No single dimension dominates; a model that wins on raw reasoning but cannot be deployed in the required region, or cannot be trusted with the data classification involved, is not a viable candidate regardless of benchmark score.

The order in which optimization happens matters as much as the criteria themselves. Prove the task is solvable at all with the strongest appropriate model first, establish that as the quality ceiling, and only then work downward — toward smaller models, routing between models by task difficulty, caching repeated results, compressing context, or, as a last resort, adaptation through fine-tuning. Teams that reverse this order and start from a cost-optimized model tend to conflate two very different failures: "the task is genuinely hard" and "the model is too weak for it." Without a ceiling established by the strongest model, there is no way to tell which one is actually happening, and cost pressure quietly becomes an excuse to under-invest in getting the task right in the first place. The full selection framework — a weighted criteria template, a benchmark record per candidate model, a routing and fallback design, and the optimization ladder from strongest-model-first through fine-tuning — is worked through in [Model Engineering](../engineering/model-engineering.md).

## 3. Data, retrieval and knowledge foundations

An intelligence system is only as trustworthy as the evidence it reasons over, and that evidence has to be produced by governed services, not assembled ad hoc per request. This section covers the full pipeline: discovering and ingesting sources, parsing and normalizing them, organizing them under a taxonomy with usable metadata, chunking them without destroying their structure, indexing them, retrieving from them, keeping them fresh, tracing lineage back to the original source and version, and enforcing access control at every step so that retrieval never returns something the requester was not authorized to see.

The design principle worth holding onto through all of that mechanics is simple to state and easy to violate under pressure: the goal is the smallest sufficient and authoritative evidence set, not the largest possible context. It is tempting, especially once context windows grow large, to solve evidence-quality problems by including more — more documents, more history, more context — on the theory that the model will sort out what matters. In practice, irrelevant evidence competes for the model's attention, degrades the quality of reasoning over the evidence that does matter, and widens the surface available for a poisoned or injected document to influence behavior. Retrieval quality also has to be evaluated on its own terms, separately from generation quality, because a system can produce a convincing answer from the wrong retrieved evidence often enough that the retrieval failure hides behind a generation success — until it meets a case the evaluation set did not happen to cover. The full ingestion-to-retrieval pipeline specification, a context quality checklist, and a retrieval evaluation template independent of end-to-end generation are in [Context and Retrieval Engineering](../engineering/context-and-retrieval-engineering.md); [Chapter 15](chapter-15-data-and-knowledge-engineering.md) covers the governance lifecycle behind the sources themselves in full.

## 4. Prompt and context engineering

Prompt engineering and context engineering are often spoken of as the same thing, but they operate at different scopes and it is worth keeping them distinct. Prompt engineering is about instructions: the fixed wording that tells a model what to do, what format to answer in, and what examples to follow. Context engineering is about everything else present at a given decision point — the task and workflow state, retrieved sources, memory, tool definitions and their results, applicable policy, illustrative examples, and the token budget all of it has to fit inside. A carefully written prompt sitting on top of a poorly assembled context still fails, because the model is reasoning correctly over the wrong, incomplete, or stale material — the failure looks like a model problem and is actually a context problem.

Because context is assembled fresh at each decision point rather than fixed once at task start, it carries requirements a static prompt never had to meet. It must be authorization-aware, so a user never sees evidence through the model that they could not see directly. It must be source-attributed, so every claim can be traced back to where it came from. It must be fresh, so stale or superseded material is not presented as current. It must compress gracefully when it does not fit the budget, rather than being silently truncated in whatever order happened to be convenient. And it must be resistant to poisoning — a document embedding instructions for the model to follow is not a hypothetical, it is one of the best-documented failure classes in deployed agentic systems.

| **Context engineering**                                       | **Harness engineering**                                         |
|-----------------------------------------------------------------|-----------------------------------------------------------------|
| Determines what the model sees now.                            | Determines how the system completes the task.                  |
| Selects instructions, knowledge, memory and tool information.   | Runs loops, tools, state, retries, checkpoints and recovery.    |
| Manages relevance, ordering and token budget.                   | Manages execution limits, authority, escalation and completion. |
| Optimizes a decision point.                                     | Coordinates the end-to-end task lifecycle.                      |

This table is worth returning to whenever a bug report arrives that "the agent got confused" — the first diagnostic question is which side of this table the failure sits on, because the fix is different in each case. The full context architecture template, a retrieval-pipeline specification, and a context-quality checklist covering all five properties above are in [Context and Retrieval Engineering](../engineering/context-and-retrieval-engineering.md).

## 5. Tool and action engineering

A tool, in this methodology, is a governed interface through which the system retrieves information, performs a calculation, or takes an action in the world — not a raw technical connection to an API. That distinction matters because a raw API assumes a human developer read the documentation before wiring up a call; a tool exposed to a model has to be narrow and unambiguous enough that the model selects it correctly at runtime, and has to assume its caller's judgment can be manipulated by adversarial input somewhere upstream in the context.

The contract that makes a tool governable, rather than merely callable, has to define its purpose; its inputs and outputs; how it authenticates and, more specifically, what it authorizes against (the requesting user and business context, not just the calling service's own identity); the classification of the data it touches; how its inputs are validated at the boundary; whether calling it twice with the same arguments is safe (idempotency); how long it is allowed to run and what happens on timeout; whether and how it retries; where transaction boundaries sit; when it requires an explicit human confirmation before acting; what it logs for audit; how a completed action can be rolled back or compensated; and what its failure looks like in a form the harness can act on, rather than free text a human has to interpret. Tools should be built narrow enough that their blast radius is controlled and clear enough that a model reliably picks the right one — a tool that can do too much, or that overlaps ambiguously with another tool, invites exactly the kind of misuse this contract exists to prevent. The full tool contract template, a worked example, integration-pattern selection guidance, and standardized tool-catalogue registration fields (including for protocols such as MCP) are in the [Tool and Integration Interface Specification](../engineering/tool-and-integration-interface-specification.md).

## 6. Agent-harness engineering

The harness is the software scaffold that sits around the model and turns a single inference call into a working system. It assembles context at each decision point, invokes the model, registers and calls tools, records state as the task proceeds, processes and validates results before acting on them, enforces the operating limits placed on the task, pauses to request human approval where the specification requires it, retries operations safely, checkpoints long-running work so it can survive a restart, and terminates on criteria that are explicit rather than implied by running out of steps.

It is worth being precise about what kind of failure the harness is responsible for, because it is a different kind from a model or context failure. A context failure produces a wrong answer to a well-posed question; the model reasoned correctly over the wrong evidence. A harness failure produces a system that never terminates, that retries a non-idempotent action a second time and duplicates its side effect, that loses track of partial progress after a crash, or that cannot distinguish "the task succeeded" from "the task simply ran out of iterations." These are conventional distributed-systems failures, and they respond to conventional distributed-systems engineering — state machines, idempotency keys, checkpointing, circuit breakers — rather than to a better prompt. And because harness assumptions are load-bearing, they have to be retested whenever the models, tools, or workflows underneath them change; a harness built and tuned against one model's behavior can develop silent gaps when the underlying model is swapped or upgraded. A harness responsibility checklist, pattern-specific implementation notes, a state-machine template, and a limits-and-budgets configuration are in [Harness and Orchestration Engineering](../engineering/harness-and-orchestration-engineering.md).

## 7. Workflow and orchestration engineering

Not every task needs an agent, and the discipline of orchestration engineering starts by choosing the least expensive pattern that actually fits the task, then justifying anything more elaborate. Use a deterministic function for a fixed calculation — it is faster, cheaper, and easier to test than any model-driven alternative, and choosing an agent for it is strictly worse on every axis. Use an explicit workflow when the path is known and enumerable, even if it branches. Reserve agents for genuinely open-ended tasks that require dynamic choice the workflow author cannot fully anticipate in advance. And reach for multi-agent systems only when specialization, isolation, or parallelism produces a measurable benefit over a single agent — not because a multi-agent design sounds more sophisticated. An unjustified escalation up this ladder is not a stylistic choice; it is a cost, reliability, and testability regression that should be treated as an architecture-review finding.

Once the pattern is chosen, orchestration covers how components hand off to each other: sequential steps where one output feeds the next, concurrent steps running in parallel with results merged, routing that classifies a task early and sends it down a specialized path, explicit hand-off where one agent transfers ownership of a task to another, a supervisor that delegates to and monitors specialized sub-agents, and human-in-the-loop steps treated as first-class nodes in the flow rather than exceptions bolted on afterward. Every one of these patterns needs the same three things to be production-grade: state that survives the pattern's own hand-offs, a named accountable owner for each path, and a defined recovery behavior for when a step fails partway through. The decision tree for choosing a pattern, and implementation-level notes and common pitfalls for each one, are in the [Reference Architecture's orchestration-pattern section](../architecture/oasis-reference-architecture.md#4-selecting-the-orchestration-pattern-ch-14-7-decision-rule) and in [Harness and Orchestration Engineering](../engineering/harness-and-orchestration-engineering.md).

## 8. Memory and state engineering

State and memory are easy to conflate and worth separating precisely. State records the current execution — the steps taken, artifacts produced, approvals granted, tool results received, errors encountered, and transaction status of the task in front of the system right now. Memory retains information that may inform future work, beyond this task's lifecycle. The distinction has a quick test: if a piece of information becomes meaningless the moment the current task ends, it is state; if it should still matter the next time this user, case, or system interacts with the agent, it is memory.

Memory, once introduced, needs the same governance discipline any other persistent store needs, and this chapter is explicit that memory must not be equated with indefinite conversation storage. The path-of-least-resistance implementation — simply keep every conversation forever and let the model search over it — quietly creates a permanent, growing, unaudited data store with no defined purpose, no retention policy, and no way to answer a correction or deletion request. A properly engineered memory store instead defines, for every category of retained information, its purpose, its source and confidence (a fact the system inferred is not the same class of memory as a fact a user explicitly stated), who can access it, how long it is kept, how it can be corrected, when it expires, and what controls prevent it from being contaminated — whether by an honest error compounding forward or by deliberate memory poisoning. A memory store with no correction mechanism will, given enough production time, silently accumulate wrong memories that degrade every future decision reading from it. The classification table, a memory-policy template per store, and a checkpoint-and-recovery checklist for harness state are in [Memory and State Engineering](../engineering/memory-and-state-engineering.md).

## 9. Human–AI interaction, structured outputs and validation

How the system presents itself to a human, and how it hands off to another machine, are both engineering problems, not interface polish applied at the end. For human-facing interaction, this means deliberately designing how evidence is presented, how uncertainty is communicated rather than hidden behind false confidence, how a proposed action is previewed before it happens, how approval and override are captured, how a human's correction is fed back into the system, when the system escalates rather than proceeds, and how ordinary feedback is collected and used.

For machine-consumed outputs, the discipline is different in kind: outputs need explicit schemas, deterministic parsing, and business-rule validation before anything downstream acts on them — "the model usually gets the format right" is not a validation strategy. And for high-consequence decisions, whether the consumer is a human or a downstream system, the system should expose its sources and the relevant reasoning evidence directly, rather than asking anyone to trust an unverifiable narrative explanation of how it arrived at a conclusion. A plausible-sounding justification is not the same thing as a checkable one, and the difference matters most exactly when the decision matters most. The [Human–AI Workflow Blueprint](chapter-32-templates-checklists-and-tools.md#7-human-ai-workflow-blueprint) is the artifact that carries this design through build and review, and [Chapter 16 — Human–AI Workflow and Experience Engineering](chapter-16-human-ai-workflow-and-experience-engineering.md) treats the interaction design itself in full depth.

## 10. Guardrails, reliability and recovery

No single control catches every failure, which is why guardrails are engineered as layers rather than a single checkpoint: input, context, model, tool, workflow, output, runtime, and business policy each carry their own controls, so a failure that slips past one layer is still caught by another. On top of that layered structure sit the operating limits that bound the system's behavior in absolute terms — iteration, time, token, cost, and transaction limits — along with the recovery behaviors that activate when something goes wrong anyway: safe retries that only touch idempotent operations, explicit handling of partial completion rather than silent inconsistency, compensating actions for anything irreversible, a defined fallback to a simpler model or workflow when the primary one degrades, a clear trigger and target for human escalation, and, at the outer edge, suspension and kill switches that stop the system outright.

None of this is optional hardening added after a system otherwise works; it is what makes autonomous operation defensible in the first place. A system with strong guardrails but no evaluation coverage has no way to know what it is actually protecting against; the reverse pairing is covered next. A pattern library mapping each guardrail type to the specific failure mode it addresses, and cross-referenced against the security threat model, is in [Evaluation and Reliability Engineering](../engineering/evaluation-and-reliability-engineering.md#3-guardrails-and-recovery-pattern-library), and the containment and kill-switch mechanics are detailed in the [security threat and control checklist](../security/agentic-ai-threat-and-control-checklist.md).

## 11. Evaluation engineering

Evaluation is how a team knows, with evidence rather than confidence, that a system is behaving acceptably — and it has to measure at more altitudes than a single response. This chapter names fifteen dimensions worth tracking: intent understanding, correctness, groundedness, citation accuracy, structured-output validity, retrieval quality, tool selection and argument correctness, workflow completion, policy adherence, escalation correctness, robustness under adversarial or edge-case input, latency, cost, user acceptance measured by behavior rather than survey, and outcome contribution — whether the system's behavior actually moves the business metric it was built to move.

That last dimension is the reason evaluation has to progress through units, not stop at the first one that's convenient to test. A single model response can be graded in isolation; a single agent step can be graded in the context of the task so far; a completed multi-step workflow can be graded end to end; and, ultimately, production behavior can be measured against the actual outcome metric. A system that only tests at the response level has no evidence it works end to end, because individually correct steps do not automatically compose into a correct outcome. A system that only measures at the outcome level has no diagnostic power when that metric moves the wrong way — it can tell you something broke, not what. Maintaining coverage at every level, not just the extremes, is what turns evaluation from a demo confidence check into an actual production instrument. The full evaluation-dimension reference, the response-to-outcome progression ladder, and a grader-design and calibration checklist for LLM-as-judge setups are in [Evaluation and Reliability Engineering](../engineering/evaluation-and-reliability-engineering.md).

## 12. Runtime, AgentOps and adaptation

Once a system is live, engineering does not stop — it shifts to versioning, tracing, and disciplined diagnosis. Every component that can change — models, prompts, context policies, retrieval indexes, tools, workflows, and controls — needs to be versioned independently, because "what changed" is the first question of any production incident, and a system that cannot answer it precisely turns every incident into an investigation instead of a lookup. Tracing has to cover model and tool calls, decisions, approvals, and outcome events, so that a failure can be diagnosed at the layer actually responsible for it — a retrieval problem, a harness bug, a guardrail gap, a genuine model limitation — rather than defaulting to whichever layer is easiest to blame or easiest to change.

Fine-tuning belongs at the end of this list deliberately. It is considered only when a failure is repeated, well-defined, and specific to the model's domain knowledge or behavior, and only after context, workflow, tool, and instruction improvements have already been tried and have failed to close the gap. It is not the default repair for every quality issue, and treating it as one tends to produce an expensive, slow-to-iterate fix for a problem that a cheaper context or workflow change would have solved in a fraction of the time. The [Model Engineering](../engineering/model-engineering.md#5-fine-tuning-decision-checklist) article's fine-tuning decision checklist operationalizes exactly this ordering, and the [Monitoring specification](../monitoring/observability-and-telemetry-specification.md) defines the trace and version record every runtime event should carry.
