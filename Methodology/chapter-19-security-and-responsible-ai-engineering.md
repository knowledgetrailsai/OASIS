# Chapter 19: Security and Responsible AI Engineering

# Security and Responsible AI Engineering

> **CHAPTER PURPOSE** Embed defense-in-depth security, misuse prevention, fairness, transparency, human control and containment throughout the lifecycle.

## Background and context

Chapter 18 built the evidence system that tells a team whether an intelligence system is good enough to ship and stays good enough once it is live. That evidence system has a blind spot by construction: an evaluation dataset, however thorough, is built from the failures a team could imagine or has already seen, and says nothing about what happens when someone deliberately engineers an input to make the system fail in a way nobody imagined. That is this chapter's territory. Where Chapter 18 asks "does this system behave correctly under the conditions we tested," Chapter 19 asks "what happens when an adversary, a compromised dependency, or an honest user's mistake pushes the system outside every condition we tested" — and treats that question as inseparable from a second one: even a system nobody is attacking can still cause real harm through bias, opacity, or an absence of meaningful human control, and responsible AI engineering is the discipline that keeps that harm from being the system's default behavior rather than an edge case someone eventually notices.

The two halves of this chapter's title are, in practice, one discipline wearing two names. A defense-in-depth control that stops a prompt-injection attack also prevents an honest user's ambiguous request from cascading into an action nobody authorized; a containment procedure built to stop a compromised agent is the same mechanism reached for when a perfectly benign agent misbehaves because of a stale index or a runaway loop. That overlap is deliberate — treating security and responsible-AI engineering as separate workstreams run by separate teams is how organizations end up with a security review that never asks whether the system is fair, and a fairness review that never asks whether an attacker could manipulate it.

This chapter sits between two others that depend on it in opposite directions. Chapter 18's robustness testing under adversarial and out-of-distribution input is the evaluation-side twin of the controls described here, and a failure surfaced through evaluation is frequently the first evidence of a security gap rather than a purely quality one. Chapter 20, immediately following, takes the responsible-AI properties and containment discipline defined here and turns them into something a regulator, auditor, or enterprise risk committee can actually inspect: obligations, evidence, and accountable owners. Chapter 19 builds the controls; Chapter 20 proves you have them.

This chapter is deliberately written at the level of "why and what," not "how and with which specific control." The direct implementation companion is the [Security: Agentic AI Threat Model and Control Checklist](../security/agentic-ai-threat-and-control-checklist.md), which turns the eight control layers and the threat model below into a fillable instrument mapped against the OWASP Top 10 for LLM Applications, the OWASP Top 10 for Agentic Applications, and MITRE ATLAS's adversary tactics. The enterprise identity and trust model every per-system control ultimately depends on is architected once in [Architecture Perspective 8 — Security and Trust Architecture](../architecture/perspective-08-security-and-trust-architecture.md), and the [OASIS Reference Architecture's defense-in-depth overlay](../architecture/oasis-reference-architecture.md#3-defense-in-depth-overlay) shows precisely where each of the eight layers below sits inside a concrete system diagram rather than as a free-floating list.

## Defense-in-depth control layers

No single control is trustworthy on its own, because no single control anticipates every way it can be defeated — an input filter can be bypassed by a novel encoding, a tool allow-list undermined by a compromised credential, a model's own safety training worked around by a sufficiently creative prompt. Defense-in-depth is the answer: rather than betting the whole system on one control being perfect, OASIS layers independent controls across the entire path a request takes, from the moment it enters the system to the moment its consequences land in a system of record, so a failure at any one layer is caught by another rather than propagating unchecked.

| **Layer**  | **Representative controls**                                                              |
|------------|--------------------------------------------------------------------------------------------------|
| Input      | File validation, malicious content detection, PII handling, rate and size limits.        |
| Context    | Source trust, authorization filters, provenance, data minimization, injection isolation. |
| Model      | Instructions, safety behavior, restricted capabilities, model-provider controls.         |
| Tool       | Allow lists, schemas, least privilege, confirmation, transaction and spend limits.       |
| Workflow   | Approvals, segregation of duties, checkpoints, escalation and compensation.              |
| Output     | Grounding, policy, privacy, schema and business-rule validation.                         |
| Runtime    | Sandboxing, network limits, secrets, step/time/token budgets and containment.            |
| Operations | Monitoring, incident response, revocation, rollback, kill switch and audit.              |

The layers are ordered deliberately, following the path a request actually takes through the system, and each earns its place by covering ground the layers around it cannot. Input and Context controls exist because an attacker's most direct route into an agentic system is the evidence it is given to reason over, not the model itself — untrusted content, whether from a user, a document, or a third-party data source, has to be treated as potentially adversarial the moment it crosses the enterprise trust boundary, never trusted by default on the strength of where it claims to come from. Model-layer controls are necessarily the thinnest layer in the stack, because a model's own safety training and instruction-following behavior is a property of a provider's model, not a component built and tested in-house — which is exactly why the layers on either side of it, Context and Tool, are engineered to hold even when the model layer alone would not.

Tool and Workflow controls are where an agent's decisions become real-world actions, and they carry the corresponding weight: least-privilege tool access, spend and transaction limits, and approval checkpoints exist because a model's output is only ever a proposal until a tool executes it, and that execution step is the last point at which a bad decision can be caught before it reaches a system of record. Output validation closes the loop on what the user or downstream system actually receives — grounding, schema and business-rule checks catch the fluent-but-wrong response that upstream controls could not fully prevent. Runtime and Operations assume everything above them will eventually fail in some way nobody anticipated: sandboxing, budgets and containment bound the damage while a failure is happening, and monitoring, incident response and kill switches make it possible to detect and stop that failure once it starts. The [Security checklist's mapping of these eight layers to the OWASP LLM Top 10](../security/agentic-ai-threat-and-control-checklist.md#1-defense-in-depth-control-layers-ch-19-mapped-to-owasp-llm-top-10) turns this into a per-layer, per-vulnerability-class instrument with a named artifact and owner for each row, and the [Reference Architecture's defense-in-depth overlay](../architecture/oasis-reference-architecture.md#3-defense-in-depth-overlay) shows exactly where in a concrete system diagram each layer's controls are enforced.

## Agentic threat model

An agent that can choose and execute actions has an attack surface a static model simply does not, which is what makes agentic threat modeling its own discipline rather than a restatement of conventional application security. Threat modelling covers prompt and context injection, malicious or compromised tools, excessive agency, identity confusion, memory poisoning, secret leakage, insecure inter-agent communication, supply-chain compromise, goal manipulation, cascading failures and denial of wallet. Prompt and context injection is the entry point most attackers reach for first, because it requires no privileged access — only the ability to place adversarial text somewhere the system will read it, whether in a user message, a retrieved document, or a third-party API response. Excessive agency and identity confusion are threats specific to autonomy itself: a system that can act on an attacker's behalf, or that cannot reliably distinguish the authority it is acting under, turns a successful injection into a real-world consequence rather than a contained anomaly. Memory poisoning and insecure inter-agent communication extend the same logic across time and system boundaries — a single successful manipulation, left undetected, can persist in memory or propagate to every agent that trusts its output.

Multi-agent systems compound this threat model rather than merely repeating it: every additional agent is an additional trust boundary, an additional surface for shared-state corruption, and an additional path by which a compromised instruction can propagate before a human or a guardrail ever sees it. This is why the [orchestration-pattern decision rule](../architecture/oasis-reference-architecture.md#4-selecting-the-orchestration-pattern-ch-14-7-decision-rule) treats multi-agent design as something that has to earn its complexity through measured benefit — an unjustified multi-agent design is a security finding as much as it is an architecture one.

Naming these eleven threats in prose is a starting point, not an endpoint — the field moves quickly enough that a hard-coded, chapter-length taxonomy would be stale within a year. The concrete instrument is the [Security checklist's agentic threat model mapping](../security/agentic-ai-threat-and-control-checklist.md#2-agentic-threat-model-ch-19-mapped-to-owasp-agentic-top-10-and-mitre-atlas), which ties each threat above to its nearest category in the OWASP Top 10 for Agentic Applications and to the specific MITRE ATLAS tactic an attacker would use to get there — OWASP for what can go wrong, ATLAS for how an attacker gets there, which is why ATLAS is the right reference for red-team scoping rather than a build-time checklist alone. That checklist also flags two OWASP Agentic categories not yet named explicitly here — unexpected code execution and human-agent trust exploitation — worth tracking even without a dedicated row above. And because every one of these threats depends on an agent's identity and the trust boundary it operates within, [Architecture Perspective 8 — Security and Trust Architecture](../architecture/perspective-08-security-and-trust-architecture.md) is where that identity model — how credentials are issued, scoped and revoked, and how inter-agent calls inherit rather than escalate authority — is designed once at the enterprise level.

## Responsible AI properties

Security controls stop a system from being made to fail by an adversary; responsible AI properties are what stop a system from causing harm even when nothing is attacking it, and both have to be engineered rather than assumed. A system is expected to demonstrate **validity and reliability** for the intended population and conditions — behaving correctly not only on the cases a team happened to test, but across the population it will actually serve, which is precisely the discipline [Chapter 18's evaluation hierarchy](chapter-18-evaluation-and-reliability-engineering.md#evaluation-hierarchy) exists to verify. **Safety, security and resilience** under foreseeable misuse and failure is this chapter's own territory — the defense-in-depth layers and threat model above are how that property gets engineered rather than merely asserted.

**Fairness and harmful-bias assessment** has to be scoped to the groups actually affected by a given system's decisions rather than treated as a single universal test — a hiring-adjacent system and a fraud-detection system carry materially different fairness obligations, and that assessment belongs in the evaluation dataset described in Chapter 18, not bolted on afterward. **Privacy, data minimization and purpose limitation** means a system collects, retains and uses only the personal data its stated purpose actually requires — a discipline that becomes a binding legal obligation the moment personal data crosses into a regulated jurisdiction, which is exactly where Chapter 20 picks up. **Transparency** about AI use, capabilities, limitations and generated content, and **explainability** sufficient for the decision, review and contestability context at hand, both exist so the humans relying on a system's output are never left assuming a capability it does not have. **Human accountability, oversight, appeal and remedy** closes the loop: every property above is only as real as the humans' actual ability to review a decision, understand it, and correct it when it is wrong.

These seven properties are named here at the level of what a responsible system must demonstrate, not how to test for it — that operational depth already exists and should not be re-derived per engagement. The [Security checklist's responsible-AI properties table](../security/agentic-ai-threat-and-control-checklist.md#3-responsible-ai-properties-where-deeper-standards-guidance-lives) points each property to where it is operationalized: validity and reliability to Chapter 18 and the NIST AI RMF's Measure function, fairness to the NIST Generative AI Profile and ISO/IEC 42001 Annex A, privacy to the DPDP Act checklist and the broader overlays indexed in the [Regulatory Framework Alignment Index](../references/regulatory-framework-alignment-index.md), transparency and human oversight to the EU AI Act's Articles 13, 14 and 50, and explainability to ISO/IEC 42001 Annex A.9.

## Containment and emergency control

Every action-taking system defines its maximum blast radius: accessible data, systems, transaction value, case volume, time window and downstream authority. That definition is the single most important artifact in this section, because it answers the question every incident review eventually asks — "how bad could this have been" — before the incident happens rather than during the scramble to reconstruct it afterward. A blast radius that has never been written down is a blast radius nobody has actually thought through; defining it forces an explicit answer to what data the system can touch at maximum authority, which enterprise systems and APIs it can reach directly or through a tool, the largest single action or time-windowed aggregate of actions it can take before triggering review, and what real-world authority its output carries — whether it auto-executes or waits on a human.

Emergency controls must be usable by operations without development intervention and tested periodically. This requirement exists because the moment a containment procedure is actually needed is, almost by definition, the worst possible moment to discover that suspending an agent requires a code deployment or a procedure nobody has rehearsed. A kill switch that has never been drilled is not a functioning kill switch — it is an assumption, and assumptions are exactly what containment procedures exist to replace with tested fact. Suspension should preserve evidence and transition work to a safe manual or deterministic path: the act of stopping a misbehaving system must not, in the process, destroy the trace record that explains what went wrong, or leave in-flight work stranded with no route to completion.

This section stays at the level of what containment must achieve rather than a step-by-step procedure, because the procedure belongs in an operational artifact a team actually fills in and tests — the [Security checklist's containment and emergency control checklist](../security/agentic-ai-threat-and-control-checklist.md#4-containment-and-emergency-control-checklist), which turns the requirements above into ten specific, ownable items: accessible data and systems, transaction-value and case-volume limits and the window over which they reset, a named kill-switch owner who is not required to be a developer, the date and result of the last suspension drill, confirmation that suspension preserves evidence rather than discarding in-flight state, and the safe fallback path work transitions to. At enterprise scale, this discipline has to operate above any single system, because a shared component's failure — a compromised model route, a shared integration, a poisoned knowledge domain — has a blast radius spanning every system consuming it; [Architecture Perspective 9 — Operations and Observability Architecture](../architecture/perspective-09-operations-and-observability-architecture.md) defines the tiered kill-switch authority that makes enterprise-wide containment possible, from a single system owner suspending their own agent, through a platform owner suspending a shared component for every consumer at once, to an AI governance forum chair's emergency authority to suspend autonomous execution across the entire agentic estate.
